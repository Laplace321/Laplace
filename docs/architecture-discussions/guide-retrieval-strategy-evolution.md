# 链路 C 攻略检索策略演进讨论

## 背景

链路 C（攻略文档检索）当前使用 BM25 chunk 级检索，在实际使用中暴露召回不足问题：
- 查询"剑阶戴冠配队推荐"时 top_k=3 未命中"具体打手分析"和"组队思路"章节（trace 6a31e65f）
- 根因：BM25 纯关键词匹配，"配队推荐"与"打手分析/组队思路"无词汇重叠，加上 top_k=3 截断导致关键内容丢失

## 候选方案对比

### 方案 A：增大 top_k + 同义词扩展

保持 BM25 分块检索，提高 top_k（3→6）+ 查询时同义词扩展。

| 维度 | 评估 |
|:---|:---|
| 当前效果 | 中等。缓解截断问题，但同义词维护成本高 |
| 扩展性 | ❌ 差。文档增多后噪声增大，同义词表爆炸式增长 |
| Token 成本 | ⚠️ 线性增长。top_k=6 每次多传 ~3k token |
| 维护成本 | ❌ 高。每新增领域需手工维护同义词映射 |
| 实现复杂度 | ✅ 低 |
| 适用场景 | 文档 <5 篇、术语稳定的短期过渡 |

### 方案 B：全文传入（不分块）

跳过 BM25，将匹配到的整篇攻略直接作为 context 传给 LLM。

| 维度 | 评估 |
|:---|:---|
| 当前效果 | ✅ 最好。LLM 完整看到所有章节，无召回遗漏 |
| 扩展性 | ❌ 差。文档 >10 篇或单篇 >10k token 时 context window 不够 |
| Token 成本 | ⚠️ 不可控。单篇扩展到 500 行时单次 10k+ input token |
| 维护成本 | ✅ 最低 |
| 实现复杂度 | ✅ 最低 |
| 适用场景 | 文档 <5 篇、单篇 <5k token 的早期阶段。不适合作为长期架构 |

### 方案 C：向量语义检索（Embedding）

用 Embedding 模型编码文档块和查询，通过余弦相似度做语义匹配。

| 维度 | 评估 |
|:---|:---|
| 当前效果 | ✅ 最好。语义匹配自然解决同义词问题 |
| 扩展性 | ✅✅ 最好。文档增多只需重新 embed，支持跨文档语义关联 |
| Token 成本 | ✅ 最优。精准召回，context 最小化 |
| 维护成本 | ⚠️ 中等。需选择 Embedding 模型、管理向量存储 |
| 实现复杂度 | ❌ 最高。需引入 Embedding API + 向量数据库 |
| 额外依赖 | Embedding 模型 + 向量存储（FAISS/ChromaDB） |
| 适用场景 | 文档 >10 篇、需跨文档语义检索的长期生产架构 |

### 方案 D：文档级 BM25 + 全文混合（渐进式）

先用 BM25 在文档级别筛选候选文档，再将命中文档全文传入 LLM。

| 维度 | 评估 |
|:---|:---|
| 当前效果 | ✅ 好。文档级匹配比 chunk 级更鲁棒，全文传入消除分块遗漏 |
| 扩展性 | ⚠️ 中等。文档级 BM25 比 chunk 级更稳定，但单篇过长仍有 token 问题 |
| Token 成本 | ⚠️ 可控。只传命中文档全文，比 chunk top_k=6 精准，比纯全文节省 |
| 维护成本 | ✅ 低。无需同义词表、无需向量模型 |
| 实现复杂度 | ✅ 低。现有 BM25 改为文档级评分 + 全文返回 |
| 适用场景 | 文档 5-20 篇、单篇 <8k token 的中期过渡架构 |

## 决策：渐进式演进路线

```
当前（1篇文档）     中期（5-20篇）       长期（20+篇）
方案 D ──────────→  方案 D ──────────→  方案 C
文档级BM25+全文     文档级BM25+全文      向量语义检索
```

| 阶段 | 推荐方案 | 触发升级条件 |
|:---|:---|:---|
| 现在 | 方案 D（文档级 BM25 + 全文传入） | — |
| 中期 | 继续方案 D | 单篇 >8k token 或文档 >20 篇 |
| 长期 | 方案 C（向量检索） | 需跨文档语义关联、或 BM25 召回率不足 |

### 决策理由

1. **方案 D 是当前投入产出比最高的选择**：改动小（chunk 级 → 文档级 BM25）、效果好（全文传入消除分块遗漏）、为方案 C 预留接口（`_vector_search` 已预留）
2. **避免方案 B 的"不可扩展"陷阱**：全文传入虽然当前有效，但无法作为长期架构
3. **避免方案 A 的"维护地狱"**：同义词表随领域扩大爆炸式增长
4. **方案 C 当前属于过度工程**：仅 1 篇文档，引入 Embedding 基础设施 ROI 不合理
5. **方案 D 到方案 C 的迁移成本低**：文档级 BM25 作为粗筛层可保留，向量检索作为精排层叠加

### 实施要点（方案 D）

- `GuideRetriever.search()` 改为文档级评分：同一文档的所有 chunk 分数取 max/sum 作为文档分数
- 返回命中文档的所有 chunk（而非 top_k 个 chunk），等效于全文传入
- `_vector_search()` 接口保留，未来方案 C 升级时实现
- `top_k` 参数语义变为"最多返回几篇文档"而非"几个 chunk"
