# 两阶段路由架构讨论

## 背景

当前路由采用单体 Prompt（~19k chars / ~6k tokens），在一次 LLM 调用中同时完成三项任务：
1. 链路分发（判断 A/B/C）
2. Skill 选择（链路 A 的具体 Skill 组合）
3. 参数提取（Skill 参数、atlas_query 参数等）

随着链路 B/C 的规则不断增加（规则 17/20/21 + 排除条件 + atlas_query 提取规则），Prompt 持续膨胀，规则互相干扰导致误路由频发。

### 典型误路由案例

- **trace 456f00c3**：「剑阶出星推荐」被规则 21（攻略知识问答）中的"推荐"关键词误判为链路 C，实际应走链路 A（按职阶+效果筛选从者）
- 根因：链路 C 的规则与链路 A 的规则存在关键词重叠（"推荐"），LLM 在复杂规则集中无法正确消歧义

## 方案对比

### 方案 A：代码预分类 + 精简 Prompt（最轻量）

在 LLM 路由之前，用确定性代码（关键词/正则）做粗粒度链路预判。

- **优势**：零 LLM 开销，可测试
- **劣势**：需维护关键词/正则规则集，边界 case 难以覆盖，长期维护成本高

### 方案 B：两阶段路由（中等改动）✅ 采纳

拆分为两次 LLM 调用：
- Stage 0（轻量分类器）：极简 Prompt（~1.8k chars），只判断 A/B/C 链路
- Stage 1（参数提取器）：只在链路 A 时调用，专注 Skill 选择 + 参数提取

- **优势**：职责解耦，每阶段 Prompt 更精简专注，分类准确率更高
- **劣势**：链路 A 多一次 LLM 调用（~200-500ms）

### 方案 C：方案 A + B 混合（最彻底）

代码预分类处理确定性 case，不确定的走 Stage 0 分类器。

- **优势**：确定性 case 零 LLM 开销
- **劣势**：架构复杂度最高，需维护代码规则 + 两套 Prompt
- **用户判断**：代码预分类需维护规则，长期不可取，B 方案更优

## 最终决策

采纳方案 B（两阶段路由），关键实施细节：

1. **Stage 0 输出格式**：链路标识 + 置信度分数（0-1），低置信度（<0.6）时走 Agent fallback
2. **Stage 0 模型**：先用同一模型上线验证架构可行性，确认后再切快速模型（渐进式）
3. **链路 B 参数提取**：Stage 0 只做分类，链路 B 再单独做一次 LLM 参数提取（职责更纯）
4. **迁移验证**：构建测试用例集（覆盖已知误路由 case + 正常 case），上线前跑通全部

## 实施效果

- Stage 0 Prompt：~1.8k chars（极简）
- Stage 1 Prompt：~15k chars（从 ~19k 精简，删除了 ~4k 链路 B/C 分发规则）
- 新增 `ClassifierResponse` Schema（pipeline + confidence）
- 新增 `classifier_output` 日志 trace phase
- 新增 `_extract_atlas_query()` 独立参数提取函数
- 测试用例集覆盖 25 个路由 case（15 A + 5 B + 5 C）
