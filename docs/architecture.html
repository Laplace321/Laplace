1. 系统概览

Laplace 是一个 AI Native 的对话式 FGO（Fate/Grand Order）数据助手。用户通过自然语言提问，系统自动解析意图、检索数据库、生成结构化回答。

核心设计理念：Two-Step RAG（路由 + 生成）架构，以 Skill-Based Architecture 实现可扩展的查询能力，配合 OneShot 优先 + Agent 兜底 的混合路由策略。

对话式交互

自然语言输入，无需记忆指令语法。支持 JSON API 和 SSE 流式两种端点。

Skill 可扩展

查询逻辑以独立 Skill 模块实现，新增维度只需新建文件 + 注册，无需改动核心路由。

多层降级

OneShot 路由 → Routing Fallback → Execution Fallback → Agent 多轮兜底，保证回复质量。

3.5 自研 DAG 图引擎与多轮对话（v0.5.0）

v0.5.0 引入自研 StateGraph（约 280 行，零外部依赖），将原本散落在 main.py / pipeline.py 的硬编码三管线重构为声明式 DAG 节点 + 条件边，并在此基础上实现 多轮对话状态机 与 SSE 节点级实时推送。

核心收益：① 节点单一职责、可测试 ② 节点级 trace_id 追踪 ③ 流式与同步统一 API ④ Checkpointer 支持 interrupt / resume 续跑。

4. 核心请求处理流程

4.1 请求入口

系统提供两个对话端点，业务逻辑完全一致：

端点方法特点
/api/chatPOSTJSON 请求/响应，适合程序调用
/api/chat/streamGETSSE 流式推送，分阶段展示思考过程

4.2 Skill 调用来源（三路径）

路径 A：Preset 展开

前端传入 preset_name，从 PRESET_REGISTRY 展开为固定 skill_calls。支持 B1 策略：用户补充文字走 LLM 路由解析额外 Skills 并合并。

路径 B：前端直传

前端传入 params（skill_calls 列表），跳过 LLM 路由直接执行。适用于 UI 交互构建的查询条件。

路径 C：LLM 路由

用户纯自然语言输入，调用 LLM 解析为 RoutingResponse（skill_calls + response_skill + fallback）。OneShot 模式：1 次 LLM 调用。

4.3 完整处理流程

1
请求接收与路由解析
main.py 接收请求，按优先级确定 skill_calls 来源：Preset > params 直传 > LLM 路由。
LLM 路由：build_routing_prompt() 构建 System Prompt → chat_completion() 调用 LLM → parse_routing_response() Pydantic 校验。
输出：skill_calls[] + response_skill + fallback
2
Fallback 检查
如果路由返回 fallback：
• greeting / out_of_scope → 直接返回 FALLBACK_TEMPLATES 模板回复
• no_match / ambiguous → 进入 Agent 兜底
• 空 skill_calls 且无 fallback → 也进入 Agent 兜底
3
SkillExecutor 执行
executor.execute(skill_calls, response_skill_name)
① Pydantic params_schema 参数校验（失败跳过并记录 rejected）
② 按 domain 分组：servant domain 走 filter AND 合并；coronation 等走 custom_context
③ 自定义 execute() 的 Skill 分别执行后取交集
④ 结果按稀有度降序 → collectionNo 升序排序
⑤ 空结果 → 尝试 resolve_nickname fallback → 仍空则标记 is_fallback=True
4
Execution Fallback 处理
如果 is_fallback=True（执行结果为空）：
① 先尝试异步 resolve_nickname（LLM 昵称识别）
② 仍失败 → build_oneshot_context() 构建已尝试条件的中文描述 → 传给 Agent 兜底
5
Context 构建与 RAG 生成
build_context() 构建预消化 Context：
• 全中文 key（名称、职阶、技能效果…）→ 杜绝 LLM 技术术语泄露
• 前 5 条代表从者详情 + 全局统计摘要（宝具卡色/职阶/稀有度分布）
• describe_filters() 将 skill_calls 转为人类可读筛选条件
ResponseSkill.build_prompt() 构建 Generation Prompt → chat_completion() 生成最终回复
6
响应返回
JSON API：返回 ChatResponse(reply, servants, count, query, model, traceId)
SSE Stream：分阶段推送 thinking / result / complete 事件

5. Skill-Based Architecture

5.1 核心机制

所有查询逻辑以独立 Skill 模块实现，通过 @register_skill 装饰器自动注册到全局 SKILL_REGISTRY。

# server/skills/base.py
SKILL_REGISTRY: dict[str, BaseSkill] = {}

@register_skill       # 装饰器自动实例化并注册
class SearchByClass(QuerySkill):
    name = "search_by_class"
    description = "按职阶筛选从者"
    def filter(self, servant, params) -> bool:
        return servant["className"].lower() == params["className"].lower()

扩展方式：新建 Skill 文件 → 在 server/skills/__init__.py 追加 import → 自动注册可用。

6. LLM 调度层

6.1 架构概览

LLM 模块 (server/llm/) 采用 适配器模式，统一封装多家 LLM 供应商的差异化 API：

server/llm/
├── __init__.py          # 公共 API: chat_completion, agent_completion
├── base.py              # BaseLLMAdapter 抽象基类
├── provider.py          # Provider 配置解析 + 两层降级调度
└── adapters/
    ├── dashscope_adapter.py   # 阿里 DashScope SDK
    ├── openai_adapter.py      # OpenAI 兼容 API
    └── obao_adapter.py        # Obao（Claude 兼容）

6.2 两层降级策略

  1. 同提供商内降级：按 models 列表顺序（如 qwen-max → qwen-plus → qwen-turbo）
  2. 跨提供商降级：当前提供商所有模型失败 → 切换下一个 Provider（如 dashscope → obao）

配置方式：.env 中 LLM_PROVIDERS=dashscope,obao + 对应 URL/KEY/MODELS 环境变量。

6.3 两大调用模式

模式函数用途特点
Chatchat_completion()路由解析、RAG 生成支持 JSON Schema 结构化输出 + Pydantic 校验
Agentagent_completion()Agent 多轮 tool-use统一走 Chat Completions API + tools 参数

7. 数据层

7.1 数据分层

Knowledge 层（自动生成，严禁手编）

server/knowledge/

  • effect_schema.json — 效果类型定义（FuncType + BuffType）
  • class_mapping.json — 职阶映射
  • class_relation.json — 职阶克制关系
  • mappings.json — 从者中文名、特性映射

来源：sync_chaldea.py 从 Chaldea Dart 源码提取

Config 层（可运营配置，支持热更新）

server/config/

  • translations.json — 中英文翻译映射
  • nicknames.json — 从者昵称映射
  • effect_overrides.json — 效果 Overlay（虚拟复合效果）
  • coronation/ — 戴冠战数据（guide/boss/team JSON）
  • uvicorn_log_config.json — 日志配置

7.2 Materialized View (MV)

server/data/servants_db.json 是运行时查询的核心数据源，由 data_loader.py 从 Atlas Academy API 拉取原始数据后构建。

MV 内烘焙字段：skillEffects、npEffects、totalCharge、npCharge、skillDetails、npDetails、traits 等，实现 O(1) 筛选匹配。

Effect Schema Overlay 机制：merge_effect_overlay() 在 runtime 将 config/effect_overrides.json 合并到 knowledge/effect_schema.json，支持虚拟复合效果（如 damageBoost、damageShield）。

7.3 从者头像本地缓存

从者头像图片采用"静态化 + 代理兜底"三层策略，解决国内用户直连 Atlas CDN 加载缓慢的问题：

  • Build-time 预下载：server/download_faces.py 在容器启动时批量下载头像到 server/data/faces/
  • Nginx try_files：生产环境优先从本地静态文件服务，未命中则代理回源 Atlas CDN
  • FastAPI 代理路由：server/face_proxy.py 开发环境提供相同行为（本地优先 + 回源缓存）

data_loader.py 的 get_face_url() 返回相对路径 /faces/f_xxx.png，前端直接请求本域。

7.4 预消化与翻译

server/translation.py 提供所有翻译映射的统一入口，从 config/translations.json 加载（热更新）。
server/context_builder.py 将英文枚举值全部预消化为中文后再传给 LLM，杜绝翻译幻觉。

8. Agent 兜底系统

定位：当 OneShot 路由/执行失败时的最后防线。采用多轮 Tool-Use 循环。

server/agent/
├── agent_loop.py     # 多轮循环引擎：LLM → tool_calls → handler → LLM → ...
├── agent_prompt.py   # Agent System Prompt
├── tool_defs.py      # Chat Completions tools 定义（3 类 7 个 tool）
└── tool_handlers.py  # Tool 执行处理器（桥接 SkillExecutor + 数据层）

8.1 可用 Tools

类型Tool延迟
核心查询search_servants — 多条件组合搜索~100ms
lookup_servant — 单从者详情~50ms
compare_servants — 多从者对比~50ms
本地查表list_effects — 列出所有效果名及别名<1ms
list_traits — 列出所有特性名<1ms
list_classes — 列出所有职阶<1ms
外部 APIlookup_skill_detail — Atlas API 技能数值~500ms

8.2 触发时机（3 个 Fallback 点位）

  1. Routing Fallback：LLM 路由返回 no_match / ambiguous
  2. Empty Routing：LLM 路由返回空 skill_calls 且无 fallback
  3. Execution Fallback：SkillExecutor 执行结果为空（含 resolve_nickname 也失败后）

9. 日志追踪系统 + BI 索引层（v0.5.1）

server/logger.py 实现多阶段事件流日志，traceId 通过 ContextVar 协程级自动传播（ADR-029），按阶段记录：

Phase记录内容
routing_input用户 query、mode、Skill 列表数量
routing_outputskill_calls、response_skill、fallback、model、usage
executionaccepted/rejected Skills、total_found、执行耗时
context_buildapplied_filters、context 大小
generation_inputGeneration Prompt 元数据
generation_output最终回复、generation_usage
node_*_input/output/error11 节点经 @with_trace 装饰器自动埋点（统一 schema）
agent_detailAgent 轮次、tokens、tool_trace
final总耗时、mode、total_tokens、metric_labels（pipeline / turn_type / skill_names / clarification_type / error_reason）

存储：JSONL（server/logs/query_trace.YYYY-MM-DD.jsonl，按北京时间天分；legacy 单文件 query_trace.jsonl 保留为只读 fallback），异步写入（asyncio.to_thread）避免阻塞 Event Loop。CLI：python -m server.logger cleanup --keep-days 30。

BI 索引层（ADR-030）：JSONL 仍是事实源，server/bi_index.py 在 final 事件触发时同步 upsert 到 SQLite (server/logs/bi_index.sqlite)，admin 后台聚合走 SQL group by。表 turn_summary 含 trace_id PK + ts / session_id / turn_type / pipeline / skill_names / clarification_type / error_reason / latency_ms / total_tokens / rating / model / query_hash。CLI 全量重建：python -m server.bi_index reindex。

告警关联：server/monitor/alerter.py 维护 _recent_failure_traces FIFO buffer（上限 5），LLM/节点失败自动 push，Bark/Telegram 通知正文渲染 /admin/logs?trace_id=xxx 链接。
